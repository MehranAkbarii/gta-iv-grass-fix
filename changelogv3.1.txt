SUMMARY
-------
1. Startup-failure paths no longer fall through as "success"
   (startup_quiescence_resume_all).
2. A failed rollback no longer frees memory that patched code may still
   point to (startup_write_failure path).
3. Removed the dead startup_quiescence_terminate_now() stub.

   (MSVC), so a memory fault there is contained instead of ending the game.


--------------------------------------------------------------------------
CHANGE 1 - startup_quiescence_resume_all(): report resume failure
--------------------------------------------------------------------------
Where: GTAIVProceduralPool.c, function startup_quiescence_resume_all().

Before:
  If one or more suspended threads could not be resumed, the code set
  g_report.status = STATUS_STARTUP_QUIESCENCE_RESUME_FAILED and then called
  startup_quiescence_terminate_now(). In your fork that function had already
  been turned into a stub that returned 0, and the caller ignored the
  result. Execution therefore fell through to the success code: the guard
  was cleared (count/active = 0), the attach gate was released, and the
  function returned 1. startup_quiescence_end() then marked the quiescence
  as completed, and the install code wrote STATUS_PATCH_APPLIED over the
  failure status. A failed resume was reported as success.

After:
  - status stays STATUS_STARTUP_QUIESCENCE_RESUME_FAILED.
  - g_startup_patch_thread_attach_gate is released (set to 0) so ordinary
    threads in DLL_THREAD_ATTACH are not left spinning behind it forever;
    startup_thread_attach_gate_waits is copied into the report as before.
  - the function returns 0.
  - guard->count and guard->active are NOT cleared, and the live handle of
    a thread that could not be resumed is kept (closing it would make the
    suspension unrecoverable).
  - callers that check the result of startup_quiescence_end() return early
    and therefore no longer publish STATUS_PATCH_APPLIED.
  - the old "#ifndef GTAIVPOOL_TEST_NO_FATAL ... #else return 0; #endif"
    block was removed (the test harness no longer exists in the fork).

Caveat: this path almost never runs (ResumeThread failing). If it does, a
thread may stay suspended and the game can hang at startup. The change makes
that outcome visible in the log instead of hiding it. The original upstream
v1.2 terminated the process at this point; your fork deliberately does not.

CHANGE 2 - failed rollback must not free live code/data
--------------------------------------------------------------------------
Where: GTAIVProceduralPool.c, label startup_write_failure.

Before:
  If rolling back the universal-behavior patch transaction (or the prior
  features) failed, the code called the no-op terminate stub and then
  continued: it ended quiescence and called gu_universal_cancel_prepared().
  That calls gu_install_abort_prepared(), which shuts down the source and
  plant banks and then calls gu_install_release_prepared(). As read, it does
  NOT check gu_patch_transaction_has_unrestored(). If any patched code still
  pointed into the prepared stubs/pools, those would be released while
  still referenced (use-after-free risk). Upstream avoided this only because
  it killed the process first.

After:
  If (!universal_restored || !prior_restored):
    - the stopped threads are resumed (startup_quiescence_end, result
      ignored),
    - g_report.status = STATUS_UNIVERSAL_BEHAVIOR_ROLLBACK_FAILED,
    - the function returns immediately.
  gu_universal_cancel_prepared() and the release of prepared allocations are
  NOT executed in this case. The prepared stubs and pools are intentionally
  retained until process exit (a few MB, only on this very rare path).
  The normal (rollback succeeded) path is unchanged.

CHANGE 5 - ownership table capacity 65536 -> 32768
--------------------------------------------------------------------------
Where: universal_pipeline.h and GTAIVProceduralPool.c.

  #define GU_OWNERSHIP_CAPACITY  65536u  ->  32768u

Effect on memory (static arrays, struct GuOwnershipTable):
  records:  GuOwnedRecord 32 bytes x N
  entities: GuEntityIndex 12 bytes x N
  total:    2.75 MiB -> 1.375 MiB  (saves about 1.4 MiB of address space and
            reduces cache footprint of every hash lookup)
GU_OWNERSHIP_MASK, GU_OWNERSHIP_PROBES (32) and GU_OWNERSHIP_RETRIES (64)
are unchanged. The loop in universal_behavior.c that scans the whole table
simply iterates fewer entries.

Safety reasoning: live ownership entries are bounded by the rendered-object
capacity (MAX_RENDERED_OBJECT_CAPACITY = 8192), so the table load is at most
25 percent, where a 32-slot probe window essentially never fills. (This
bound is my reading of the code and was not confirmed in-game: check
ownership high_watermark and insert_failures in your log.)

Compile-time checks added in GTAIVProceduralPool.c right after
MAX_RENDERED_OBJECT_CAPACITY:
  - GU_OWNERSHIP_CAPACITY must be a power of two (the table uses a mask),
  - GU_OWNERSHIP_CAPACITY >= 4 * MAX_RENDERED_OBJECT_CAPACITY.
If either is violated later (for example, if the rendered ceiling is
raised) the build fails with a negative-array-size error instead of
silently running with a table that is too small.

Not changed: the event ring (GU_EVENT_RING_CAPACITY 8192, about 557 KB).
When full it only drops statistics events, so shrinking it gains little.

Honest scale note: this saves about 1.4 MiB. It does not by itself fix any
crash; the main benefit is fewer cache misses.

CHANGE 7 - SEH guard around telemetry reads of game memory
--------------------------------------------------------------------------
Where: GTAIVProceduralPool.c, telemetry thread and helpers.

Problem found during review: the whole codebase contained zero __try
blocks, while the telemetry thread reads game memory (the procedural
manager, its buffers, definition tables) from its own thread. The pattern
is "VirtualQuery says the range is readable, then dereference", which is a
check-then-use race: if the game frees or remaps that memory in between, the
read raises an access violation in the mod's thread and takes down the whole
process. poll_exhaustion_once() runs every 100 ms for the whole session
(about 24,000 times in 40 minutes), and the full snapshot runs every 5 s.
This is a suspicion, not a proven cause of any crash.

What was added:
  - static volatile LONG g_telemetry_guard_faults  (fault counter)
  - gu_telemetry_exception_filter(): contains only EXCEPTION_ACCESS_VIOLATION
    and EXCEPTION_IN_PAGE_ERROR; every other exception continues the normal
    search, exactly as before.
  - telemetry_guard_fault(where): on the FIRST contained fault writes a
    "TELEMETRY GUARD" block to the log naming the function; later faults
    only increment the counter.
  - macros GU_GUARDED_TRY / GU_GUARDED_EXCEPT(where):
      MSVC:      __try { ... } __except(filter) { telemetry_guard_fault }
      other:     "if (1) { ... } else { }"  (compiles, but NO protection)
  - poll_exhaustion_once() was renamed poll_exhaustion_once_unguarded() and
    a new poll_exhaustion_once() wrapper calls it inside the guard.
    (tuning_safety_governor_poll() is called from inside it, so it is
    covered too.)
  - capture_telemetry_snapshot_guarded(): returns 0 on fault. It is used in
    both call sites: capture_early_telemetry() and the 5-second loop in
    telemetry_thread_main(). A fault there follows the existing
    "TELEMETRY WAIT" path (log line, Sleep(1000), retry).
  - verify_live_state_guarded(): runs verify_definition_scaling_live() and
    verify_procedural_model_draw_distances_live(), each in its own guard.

Deliberately unchanged: the 100 ms poll interval, because the same loop also
drains the event ring (a slower rate could lose more statistics events).

Note on tool chains: the guard needs MSVC. The upstream README mentions a
TinyCC build; TinyCC has no __try support, so there the code still compiles
via the fallback macro but without the protection. Your .vcxproj targets
v145 (VS2026), where the guard is active.

What this cannot do: it only covers memory reads in the telemetry thread. A
crash in the game's own thread, in the hooks, or in another mod is not
affected.

REVIEWED, NO CHANGE MADE
--------------------------------------------------------------------------
  - The first-chance vectored handler (targeted_provider_exception_logger)
    filters by exception code first, only logs once and always returns
    EXCEPTION_CONTINUE_SEARCH. Harmless.
  - crash_exception_handler (unhandled-exception filter) only writes a
    minidump for fatal exceptions and chains to the previous filter.
  - Ownership token counter is 32-bit; exhausting it would need billions of
    insertions, so it cannot explain a 40-minute crash.
  - All seven for(;;) loops have exit conditions (break/return/timeout).
  - No time-based threshold near 40 minutes exists in the code. Time
    constants are 100 ms, 5 s, 30 s and a 60 s watchdog grace (the
    watchdog is disabled by the shipped INI).
  - Hook paths (commit/release, ownership table) run in the game's own
    thread under the module's lock.

FLAGGED BUT NOT CHANGED (your decision)
  - DEFAULT_HANG_WATCHDOG is 1 in code while the shipped INI sets
    HangWatchdog=0. If the INI is missing or unreadable, the watchdog turns
    on. Setting the code default to 0 would make both agree.
  - The crash dump file is created with CREATE_NEW. If a dump with the same
    name already exists, a new crash cannot write one (the log shows
    DUMP_FILE_CREATE_FAILED). Delete old dumps before the next test. The
    log has a "Crash dump path" line.
  - PLUGIN_VERSION was not bumped.
  - The optional spawn_throttle module from earlier in the conversation is
    NOT part of this patched zip.
